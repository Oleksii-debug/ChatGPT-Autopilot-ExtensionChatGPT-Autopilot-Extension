ChatGPT Автопілот 0.9.8 — СЦЕНАРНА РОБОТА / ПРЯМЕ КЕРУВАННЯ / ПАРАЛЕЛЬНІ СЕСІЇ

Головні зміни:
- Додано окрему вкладку «Сценарна робота» з підвкладками «Цикли в чаті», «Двійки», «Аудитор + група», «Стан».
- Цикли підтримують довільну послідовність промптів, окрему кількість повторів кожного кроку, задану кількість кіл у поколінні та автоматичний перехід у новий чат/покоління.
- «Двійки» підтримують одну або багато незалежних пар аудитор↔розробник із жорстким збереженням партнерства.
- «Аудитор + група» підтримує довільну кількість розробників і бар’єр: наступний хід аудитора дозволяється лише після завершення всіх працівників поточного кола.
- Тайм-аут відповіді настроюється (типовий приклад 40/60 хв). При зависанні можна замінити лише учасника або повністю створити нову команду. Перед заміною підтримується окремий аварійний промпт аудитору; новий працівник спочатку отримує початковий промпт, потім звичайний циклічний.
- Стан сценарію переживає перезапуск: роль, чат, покоління, коло, крок, повтор, очікування, тайм-аут і кількість замін зберігаються.

Відновлено за канонічним checkpoint 0.9.7:
- строгий CHATGPT_AUTOPILOT_CONTROL_V2 у кінці відповіді координатора є основним каналом керування; GitHub лишається дзеркалом/резервом;
- пряме керування застосовується до GitHub fallback;
- опція bootstrap_pinned_control_first читає закріплений GitHub control до першого ходу координатора і може одразу матеріалізувати ADD_TASKS;
- runtime показує джерело останнього control;
- імпорт профілю вже відомого project_id вибирає існуючий оркестр;
- усі 0.9.6 exact-once/no-blind-resend гарантії збережено.

Паралельне виконання без внутрішнього конфлікту сесій:
- прибрано старий 90-секундний глобальний бар’єр між різними сесіями; кожна сесія дотримується власного minimumSendInterval;
- сучасний submit path більше не використовує один profile-wide Send lease як глобальний замок; exact-once гарантує durable SUBMITTING/AMBIGUOUS operation конкретної сесії;
- runtime виконує до 10 незалежних активних сесій паралельно за замовчуванням; технічна верхня межа — 32;
- конфігурація 5 ordinary + 5 scenario-managed окремо протестована: всі 10 входять в один паралельний batch без starvation;
- однаковий launch URL не означає спільну вкладку: незалежні сесії отримують окремі extension-owned tabs і власні tab hints;
- restart під час багатьох одночасних SUBMITTING переводить кожну операцію окремо в AMBIGUOUS recovery;
- глобальна пауза профілю лишається тільки для підтвердженого ChatGPT account-level rate limit; перша детекція встановлює один profile.rateLimitUntil, а повторні паралельні детекції тієї самої паузи не пересувають дедлайн ще на 5 хв;
- rate limit більше не переписує retryAfterAt у кожній задачі кожної сесії; до profile.rateLimitUntil нова браузерна робота не стартує, після дедлайну всі придатні сесії можуть відновитися паралельно;
- Chrome tab I/O винесено за межі серіалізованого StorageRepository.update, тому повільна навігація однієї вкладки не утримує глобальну чергу запису стану;
- launch-поверхні / та /g/<slug> ніколи не успадковують випадкову наявну вкладку: кожна незалежна Session отримує власну вкладку; повторне використання дозволяється лише для конкретної /c/<id> або durable ownership hint;
- окремо відтворено COMPOSER_LOST_AFTER_INSERT і TAB_NAVIGATION_TIMEOUT в одній із 10 смуг: збій лишається локальним, інші 9 продовжують;
- модель 10 сесій × інтервал 3 хв × 4 години дає по 80 внутрішньо дозволених send opportunities на сесію; недобір можливий лише через фактичну браузерну взаємодію, recovery/error або зовнішній rate limit ChatGPT.

Архітектурні гарантії:
- другого механізму Send немає; Scenario Work матеріалізує звичайні ONE_PASS Session/Task у чинному Core;
- завершення сценарного ходу зараховується лише після завершеної відповіді ChatGPT, а не після самого Send;
- холодний старт: Orchestration V2 -> Scenario Work -> Core execution;
- аварійне відновлення не стирає unresolved Send evidence;
- фізичний Windows/Chrome/NVDA PASS не заявляється без перевірки власником.
