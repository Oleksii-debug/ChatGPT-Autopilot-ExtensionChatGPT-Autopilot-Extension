SCENARIO POOL CONTROL + RESPONSE TELEMETRY — 2026-09-26
- Scenario Work now treats one launched CHAT_CYCLE pool as one user-facing scenario controller instead of listing each physical chat as a separate editable scenario.
- Pool-wide Start / Pause / Resume / Stop / Delete commands act on every physical member atomically; physical chats remain visible in Sessions/global status and diagnostics.
- A paused or stopped pool can update runtime-safe controls without resetting progress: response timeout, polling interval, post-response launch gap, pre-Send delay, busy-check delay, retry backoff, timeout policy, restart-on-timeout, replacement budget and first-prompt stagger.
- Prompt sequence structure, repeat counts and launch URL are immutable for an existing pool; changing those requires a new pool so differently advanced chats cannot receive a corrupted program.
- Scenario Work list shows one aggregate pool entry. Controls are moved directly below the list for keyboard/NVDA discoverability.
- Assistant-response diagnostics now record bounded state-change/heartbeat evidence: BUSY/READY/completion/probe error, wait age, deadline remaining, baseline status, streaming deadline extension and actual response timeout. Prompt/response bodies remain excluded.
- Response telemetry is rate-bounded (state changes immediately, normal heartbeat every 5 minutes, near-deadline heartbeat at most once per minute).
- Truth correction after owner example “step 1/12; Send 3/12; completed responses 1/12”: raw transport Sends are no longer projected as logical X/12 progress. CHAT_CYCLE logical progress is completed assistant responses plus at most one current in-flight verified Send. Physical retry/replacement Sends remain separately auditable.
- Timeout/replacement no longer rewinds completed CHAT_CYCLE cursor to START. A response to a historically duplicated old stage is recorded as real physical evidence but does not increment logical completedResponses. Timeout with no response proof and exhausted replacement budget is ERROR, never fake COMPLETED.

AGENT ROUTE SELECTION — AFTER THE 74EC0D2 ARCHIVE
- Agent can pin one saved, enabled global route by its route ID. Its goal/policy JSON draft retains that choice. The route pool passes the chosen endpoint ID (including `mistral`) to Gateway without changing the global profile.
- A missing/disabled route or conflict with the globally pinned route stops the model call with an explicit error. Other global constraints, role requirements, cooldown, and budget still apply. Leave the selection on inheritance for automatic failover.
- Agent status refresh no longer erases policy edits typed before Save. A save that completes after newer typing keeps the newer edits visible and marked unsaved; switching jobs loads the selected job's saved policy.

The saved route remains visible if it later becomes unavailable, and execution still fails closed before provider I/O.
- Agent usage now reports the last actual route ID and a bounded failover-chain summary. Regression coverage proves an Agent pin cannot bypass global deny policy, role filtering, or durable route backoff.
